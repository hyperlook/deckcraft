# AI 统一工作区迁移计划

状态：统一工作区迁移计划及历史规划记录。本轮已实施 M1（#20 + #12）工程切片，实际交付/门禁/未验收项见 [M1 记录](ai-m1-review.md)。下文“本轮只改文档”的描述是先前规划轮次，不是本次实现声明；没有提交、撤回原工作或运行付费模型。新产品约定见 [RFC](rfcs/ai-assistant.md)，架构见 [交付计划](rfcs/ai-assistant-architecture.md)，在线追踪 [#10](https://github.com/hyperlook/deckcraft/issues/10)。

## 结论

这次工作有保留意义，但不能作为“全稿归纳产品完成”继续推进。保留正确的安全和数据底座，替换把后台处理变成用户操作台的流程。

用户想要的是：
- 空文件的模糊需求，通过聊天中的选择题收敛，随后进入共同页面工作区。
- 已有 PPT 自动判断项目上下文是否可复用，新导入在后台建立上下文。
- 大纲/页计划直接出现在原分页列表，计划页原位展开成真实页面。
- 聊天展示动作状态与最终总结，PPT 工作区展示实际成果。

旧“先归纳确认、再改页、最后另一套新建”顺序撤销。

## 2. 保留、迁移、替换

| 当前内容 | 处理 | 依据 |
|---|---|---|
| `scripts/ai/pi-bridge/` 固定桥与有界协议 | 保留，后续扩展对话/动作事件 | 认证隔离、预算、取消无需重复建设 |
| `crates/ai/src/request.rs` 生命周期 | 保留身份/终态保护，扩展共享任务 | 不能继续把单次 summary 当完整 Agent 工作 |
| `crates/ai/src/synthesis.rs` | 保留为导入理解子步骤 | 全页来源与映射正确；空文件不能走 NoEvidence 门槛 |
| `crates/model/src/summary.rs` 及持久字段 | 迁移为项目表达计划与页状态 | 计划与原文分离有价值，confirmed 不是用户就绪仪式 |
| `crates/engine/src/ai_apply.rs`、`ai_contract.rs`、`cmd/ai.rs` | 保留校验/原子提交，补共同命令 | 独立暂存/确认可兼容，不作为正常 UX 前置 |
| `crates/engine/src/cmd/file.rs` 元数据保护 | 保留并独立回归 | PPTX 导出不能丢掉项目保存/恢复语义 |
| `crates/ui-egui/src/ai_pilot.rs`、`assistant.rs` | 替换产品流程，抽走后台编排 | 当前是归纳操作台，不是统一聊天工作区 |
| `crates/ui-egui/src/thumbs.rs`、`sorter.rs` | 后续扩展原页列表 | 当前工作尚未把页计划/动作整合到原有展示 |
| 模型选择/取消/错误 UI | 复用小组件并简化 | 自动加载模型，用户不关心桥协议和快照 |
| 新增 engine/AI 安全回归 | 保留、迁移断言 | 跨标签、迟到、保存、撤销仍是共同行为 |
| 独立归纳侧栏操作链测试 | 重写成共同体验验收 | 不能用旧测试锁死“加载—提取—勾选—确认”流程 |
| `Round::from_confirmed` 与全文回填大纲习惯 | 改造 | 需要需求+事实依据+表达计划+当前页，不能只用 Outline |

以上“保留”不是可以原样合入 main 的代码审查结论。先按底座和 UX 变更拆分审查，确认实际测试/兼容边界后，再由用户决定提交或归档；本轮不擅自 commit、stash、reset 或删除工作。

## 3. 下一轮的工作顺序

### M1：#20 + #12，一起交付共同工作区

1. 在 ai/宿主建立最小共享协调服务，迁出 UI 中的快照和任务生命周期编排。
2. 聊天入口、自动加载模型、选择题与真实动作事件先接入同一服务。
3. 新导入后台建模、原生上下文复用，以及空文件需求澄清汇合。
4. 页计划/原页概括进入原 thumbs/sorter；稳定 ID、计划态和原生保存一起验证。
5. 用户在同一个列表扫看和调整，不另外打开证据/大纲操作台。

M1 的验收目标是共同工作区和可用页计划，不冒称已经生成整份 PPT。

### M2：#15，共享执行同时支持成稿和改页

1. 用同一协调器完成计划页展开与已有页修改，受限内容调用复用当前桥。
2. 在隔离候选中构建原生页面、真实渲染校验并做有限修正。
3. 在原位置显示动作和候选，任务完成后一次安装；聊天给出真实总结。
4. 同一版本连续演示模糊主题成稿和导入改页，不分别验收两套产品。

### M3：#18 外部入口；#19 全程验收

外部入口复用同一任务、澄清和变更授权机制。验收必须覆盖保存恢复、手改后的下一轮、跨标签、取消/失败和一次任务撤销。

## 4. 禁止延续的旧假设

- 不等待独立“大纲确认”面板被验收后再建设共同工作区。
- 不等单页改写全部完成才开发新建的需求澄清。
- 不以“只有 title/points JSON”或大纲卡片作为生成 PPT 的最终交付。
- 不让用户手动管理来源快照或逐轮检查发送协议。
- 不把用户确认的推断当成事实，也不因隐藏后台步骤而取消隐私/安全保护。
- 不强行丢弃现有底座，更不把“重做 UX”解释为重新造认证、网络和 engine 历史。
