# RFC：DeckCraft AI 助手——任务、草稿与整体提交

- **文档类型**：设计 RFC，包含首版范围、接口约束与分阶段实施计划。
- **状态**：核心原则与首版方向已确认，待实现；本文描述目标行为，不代表已有能力。
- **适用范围**：原生应用内 AI 助手、CLI、控制通道与 MCP 的共享编辑语义。
- **首版目标**：先跑通现有页面文本修改，再用少量模板跑通大纲到新建文稿。
- **实施追踪**：[#1：AI 助手 MVP](https://github.com/hyperlook/deckcraft/issues/1)。

## 1. 已确认的原则

### 1.1 文档是编辑结果的唯一真相源

每次任务从当前真实文档生成按需切片，不以旧对话中的页面描述覆盖画布。
撤销后发起新任务，应读取撤销后的文档。快照不是整个 `DocState` 的序列化，
只包含目标结构、必要样式、全篇摘要与任务约束。

不把冗长聊天日志作为模型的默认上下文。但需要分别管理三类状态：

| 状态 | 内容 | 生命周期 |
|---|---|---|
| 文档状态 | 页面、形状、样式、媒体与编辑历史 | 随文档保存、撤销和重做 |
| 结构化意图 | 受众、目标、术语、事实来源、已确认大纲 | 当前任务；需长期保留的约束可进入文档元数据 |
| 任务状态 | 任务 ID、快照身份、逐页结果、错误、取消标记 | 运行期间；恢复能力后续按需持久化 |

快照可以减少陈旧上下文，但不能保证消除模型幻觉。
数据、数字和来源必须来自用户材料或已确认事实，未知信息应明确标注。

### 1.2 一次用户要求，对应一次完整改动和一条历史

**历史不与 AI 内部的小操作挂钩。** 用户一次要求可能涉及多页、多个模型请求、
多次填槽、渲染、修正和重试，这些都在隔离草稿内完成，不进入主文档的撤销栈。

完整结果通过验证后，整体应用一次，只记录一条命名历史。
一次撤销撤销整次改动，一次重做恢复整次改动。
失败、取消、冲突或无实际改动时，不产生文档历史。

这里区分两个概念：

- **历史粒度**：用户可撤销的单位是一次完整 AI 改动，不是内部工具调用。
- **提交原子性**：完整改动要么全部应用，要么主文档与历史保持不变。

任务等待期间，不开启跨越用户编辑的长事务，也不锁住主文档。
草稿预览与进度不等于提交，不能逐页写进真实文档再事后拼接历史。

### 1.3 大纲优先，简单修改保持简单

从零生成遵循：主题输入 → 可编辑大纲 → 模板选择 → 草稿生成与验证 → 整体应用。
局部文本精简直接使用选中页面与用户指令，不强制经过大纲与模板选择。

### 1.4 模板驱动，先用少量样本跑通

已有本地 `.deckcraft` 底稿作为资产来源。首版只选择 **2～3 套样本模板**，
优先文本与原生图形为主、字体可用、图片依赖简单的设计。
先建立这些样本的槽位契约并验证完整流程，再逐步扩充。

**全库验收不是首版前置条件。** 样本以外的模板暂不进入首版推荐范围。
本 RFC 不要求在接入 AI 前验证或改造整个资产库。

### 1.5 确定性处理优先，按需引入 Agent

普通填槽采用结构化模型请求与确定性执行器，无需先启动独立进程或完整多工具 Agent。
页面任务隔离、并发受限，只有复杂视觉修正才考虑有预算的工具循环。
性能目标通过基准测试建立，不承诺固定 Token 上限或全篇十秒交付。

## 2. 首版范围与非目标

### 首版包含

- 选中页文本精简或改写，保留关键事实与既有结构。
- 结构化大纲：增删页面、调序、编辑标题与要点。
- 2～3 套样本模板的页面职责与语义槽位。
- 按页有界并发、单页重试、取消、进度与隔离草稿预览。
- 完整结果的冲突检查、原子提交、单步撤销与重做。
- CLI/控制通道/MCP 复用确定性的提交能力。

### 首版不包含

- 全模板库自动适配、任意坐标自由重排与自动换风格。
- 自动文生图、联网搜集事实或未经确认的数字补全。
- 完整聊天历史保存与无限上下文 Agent。
- 多用户协同编辑、自动三方合并与静默覆盖冲突。
- 跨进程任务恢复；首版保留运行期任务状态即可。
- Web 服务商接入与凭据后端；核心契约仍保持 WASM 兼容。

样本依赖的字体与图片在样本阶段处理，不为全库预先建设庞大降级系统。
后续分发模板或素材时确认许可，不把本地验证扩大成重新分发全部资产。

## 3. 用户流程与任务状态

### 3.1 从零生成

```text
主题 / 受众 / 材料
        ↓
生成结构化大纲 → 用户编辑并确认
        ↓
选择样本模板 → 冻结任务计划与目标文档身份
        ↓
按页生成 → 确定性填槽 → 排版与事实校验
        ↓
草稿预览 → 用户应用
        ↓
检查冲突 → 整体提交 → 一条 AI 历史
```

默认向当前文档追加生成页，不静默替换已有内容；需要新文稿时，先通过现有
`file.new` 行为创建目标文档，再启动任务。AI 撤销范围是该目标文档内的整体改动，
不是打开或关闭文档等 Session 生命周期操作。

大纲包含每页的主结论、职责、要点、来源与页型建议，不仅是章节标题。
更改已冻结大纲、模板或共同事实后，创建新任务，不能复用不匹配的页面结果。

### 3.2 局部文本修改

用户选择页面并输入“精简要点”等要求。任务冻结目标页、可改文本与禁改事实，
产出草稿差异并验证，用户应用后整体替换相应内容。
请求返回时不依赖当前活动页或当前选区定位目标。

### 3.3 状态机

```text
planning → awaiting_outline → awaiting_template → generating → validating → ready → applying → applied
                                                      ↑            │                 │
                                                      └─ retry ────┘                 └→ conflicted

局部修改：直接进入 generating。
运行中：可转 cancelled 或 failed；终态响应不再修改文档。
ready：用户应用前重检目标；冲突后保留草稿，重新生成需使用新快照。
```

- 单页失败可以只重试该页，成功页保留在草稿内。
- 首版默认全部目标页验证通过才进入 `ready`，不自动提交部分成功结果。
- 用户取消、目标文档关闭后，晚到响应必须被丢弃。
- 取消与应用在主线程串行处理；整体提交后取消不再生效，用户可撤销。
- `failed` 与 `conflicted` 保留可解释错误；首版不自动合并冲突。
- 同一文档首版最多一个未结束 AI 任务，用户仍可正常手动编辑文档。

## 4. 模块边界

```text
应用宿主（拥有 Session、运行时与事件桥）
    │ 只读快照与结构化意图
    ▼
crates/ai（计划、状态机、模型适配、请求池、草稿协调）
    │ 结构化页面结果
    ▼
隔离草稿 / 模板执行器 / 验证器
    │ 进度、预览与受限补丁
    ▼
应用宿主主线程
    │ 确定性的提交命令
    ▼
crates/engine（校验目标、原子应用、历史、选区、revision）
    ▲
    │ 同一提交语义
CLI / 控制通道 / crates/mcp
```

- `engine` 定义快照身份与补丁提交契约，不依赖 `ai` 或 UI。
- `ai` 管模型调用与任务编排，不持有真实 Session 的写锁。
- egui 展示状态并发出用户操作；业务编排不放在面板代码中。
- 模板执行器使用 `format`、`model`、`text`、`render` 能力，不依赖 MCP 协议。
- MCP 是外部适配层，与 AI 共同使用引擎，不作为 AI 内部必经路径。
- 异步运行时由应用宿主适配；不得把原生线程或网络实现引入 L0～L5。
- 用户动作仍是引擎命令；纯任务控制不产生文档历史，真正应用结果才产生历史。

以下接口名为建议名称，不是已实现 API；实现阶段可调整命名，不改变契约。

## 5. 快照与补丁契约

### 5.1 快照身份

每次任务至少冻结：

| 字段 | 用途 |
|---|---|
| `job_id` | 任务身份、响应关联与重复提交识别 |
| `doc_uid` | 绑定目标文档，防止活动文档切换导致错写 |
| `base_content_revision` | 内容版本，用于判断任务快照是否过期 |
| `target_slide_ids` | 稳定目标页，不能用 UI 页序号寻址 |
| `plan_version` / `template_version` | 保证任务计划、模板和结果一致 |

现有 `DocState::revision` 也会随选区变化增加，不能直接当作内容版本。
实现应引入独立内容版本或等价内容身份：真实文档修改、撤销、重做均使其变化，
仅选择页面或对象不改变内容身份。

首版采用保守文档级冲突检查：任务期间任何内容修改都要求重新生成。
后续再用目标页内容哈希减少无关页面修改造成的冲突。
多文档切换不改变目标身份，关闭后重新打开文件也不能复用旧 `doc_uid`。

每个页面请求携带全篇叙事摘要、已确认事实与本页职责，避免隔离请求造成
重复论点、术语不一致或跨页数字冲突。按任务裁剪上下文，不设置统一 2k Token 硬承诺。

### 5.2 受限补丁

模型不直接提交任意引擎命令。首版补丁只允许：

- 替换指定目标页的指定文本字段。
- 添加经过验证的模板页面草稿。

文本地址使用 `(SlideId, ShapeId)`；复制或新增页的局部 ID 在应用时由引擎重新分配。
草稿携带必要资源与引用映射，不能仅拼接页面数组。
未知字段、未知 ID、越权目标与不支持操作均拒绝，而非尽力执行。

槽位响应示例是协议示意，不是现有 manifest 格式：

```json
{
  "page_task_id": "page-02",
  "template_page_key": "three-points",
  "slots": {
    "title": "下一阶段工作重点",
    "point_1": "明确目标用户和使用场景",
    "point_2": "验证核心流程和交付质量",
    "point_3": "依据真实反馈调整下一轮计划"
  }
}
```

模型只见语义槽位与容量；执行器把字段映射到真实页和文本对象。
纯文本与段落结构应明确区分，不把 Markdown 字符串假定为富文本。

## 6. 完整改动的原子提交与历史

### 6.1 现有能力与需要补齐的边界

`Session::execute` 支持嵌套命令只生成外层历史，但 MCP `batch` 当前是逐条调用，
既不保证整批回滚，也不保证整批只有一条历史。panic guard 是最后防线，
不能替代普通错误路径的事务语义。

因此新增一个确定性的整体提交命令，暂称 `ai.applyPatch`。
不通过逐条操作真实 Session 再压缩撤销记录来实现它。

### 6.2 提交流程

1. 在隔离草稿完成所有生成、修正和资源准备，验证格式、容量与引用。
2. 主线程确认任务可应用、目标文档存在、内容身份仍匹配。
3. 若目标有未完成指针或文本交互，等待其结束，再重新检查冲突；不吞并用户历史。
4. 在当前文档的独立候选副本上构造完整结果，不污染主文档。
5. 成功后一次安装结果与最终选区，更新内容版本，清理 Redo，写入一条命名历史。
6. 提交过程无网络、文件保存或导出；这些外部副作用不属于可撤销补丁。

所有可能失败的校验与资源处理放在安装前。普通错误或 panic 不得留下半成品，
也不得改变原历史、选区或成功提交账本。

撤销条目保存的是**提交前文档与选区**，不是生成后的文档：

```rust
// 历史内容示意；应由统一引擎提交入口维护，不让 AI 直接操作历史栈。
HistoryEntry {
    label: "AI: 生成 5 页项目汇报".into(),
    doc: Arc::clone(&old_doc),
    selection: old_selection.clone(),
}
```

需要支持动态命名标签，沿用现有 Undo/Redo 行为，不创建 AI 专用撤销栈。
重复 `job_id` 提交返回已应用结果，不重复增加页面或历史；任务成功后保持终态，
即使用户撤销，也不能因为重试响应再次应用。重新生成使用新任务 ID。
首版幂等账本按文档会话保留，并设置任务数上限；不能无限增长。
无实际变化的结果不创建历史，也不清空已有 Redo。

## 7. 样本模板契约与排版验证

已有资产的 `manifest.json` 包含逐对象文本与图片绑定。
在选定的 2～3 套样本上补充一个语义适配层，不需要重做整个资产库。
资产根目录可配置，不能把开发者机器绝对路径编译到产品中。
底稿通过现有 `format` API 加载，在独立工作副本操作，不修改原资产。

### 样本需要定义

- **页型职责**：封面、要点、对比、流程、总结等。
- **文本槽位**：标题、要点、品牌、来源；区分必填、可选、固定装饰和系统字段。
- **容量约束**：最大行数、最小字号、支持语言与必要段落结构。
- **图片槽位**：背景、内容配图或装饰；定义宽高比、裁剪和层级。
- **资源约束**：画布、母版、布局、媒体、字体和页面引用。

填充后必须处理样本品牌、日期、示例数字、来源与原图表数据，不能将示例当事实。
页数不足时优先复制同一家族的合适页型；首版不静默换成默认母版。
没有匹配页型时提示调整大纲或明确降级，不能悄悄改变整体设计。

`text.set` 复用首个 run 格式与部分段落属性，不完整保留混合字体、颜色和超链接；
自动适配也可能改变文本框尺寸。首版文本修改应限定为可安全替换的对象，
不支持的混合格式拒绝或明确提示，后续再增加细粒度富文本补丁。

溢出修正顺序：压缩措辞 → 换同家族页型或拆页 → 在约束内调整字号。
未知事实不因缩写被改变。先检查布局，再渲染检查遮挡、裁剪和留白。
允许设计性的图文重叠，不能把所有矩形相交一律当错误。

缺字体在样本中明确选择可用字体并重新验证换行；不擅自安装或分发字体。
无自动图片生成时，样本使用原生装饰、许可明确素材或明确设计的占位区域，
不保留破损图片和调试标签；依赖关键背景图片的样本须先处理该背景。

## 8. 模型适配、并发与安全

### 8.1 请求池

- 首版接入一个明确配置的服务商，模型适配与业务契约分离。
- 页级并发初始上限为 4，可配置；这不是 RPM/TPM 限流的替代品。
- 定义输入与输出预算、任务总期限、单页超时、重试次数和费用上限。
- 重试遵循指数退避与 `Retry-After`，只重试可恢复错误。
- 取消停止派发并尝试中止在途请求；无法中止时仍必须丢弃晚到结果。
- 先做确定性验证，再对需要修正的页发请求，修正轮数受限。

性能分别记录大纲首次可见、确认后的首个草稿可见、整篇通过验证的耗时，
报告 P50/P95、失败率、重试率和费用。人工确认时间单列，不计入模型生成耗时。

### 8.2 安全与隐私

- schema 与白名单在引擎边界重新校验，不能只信任模型或 AI 协调层。
- 限制页面数、补丁数、字符串长度、资源尺寸与递归深度。
- 模型不获取任意文件路径、文件命令或通用 `run_command` 权限。
- 文档内容属于数据，其中的指令不能扩大任务权限或上传范围。
- 发送前明确服务商与上传范围；首版只发送必要文字结构，不默认上传整份文件。
- 凭据使用宿主安全存储或明确的会话配置，不写入文档、日志或仓库。
- 默认不落盘完整 prompt 与敏感正文；最小诊断记录有保留和清理规则。
- Web 后续通过用户凭据或受控后端接入，不能在客户端内置服务商密钥。

## 9. 分阶段实施计划

每个阶段单独分支、单独 PR，前一阶段合并后再推进依赖阶段。
先用 fake provider 验证契约与失败路径，再用真实模型验证效果与耗时。

| 阶段 | 主要交付 | 前置 | 验收 |
|---|---|---|---|
| P0 契约与离线夹具 | 快照、补丁、任务状态、样本选择、fake provider | 本 RFC | 输入边界与完整状态流有测试，不需网络 |
| P1 引擎整体提交 | 内容身份、稳定寻址、原子应用、动态历史、幂等 | P0 | 一次要求一条历史；失败零改动；撤销重做准确 |
| P2 AI 任务协调 | 适配器、隔离草稿、请求池、取消与单页重试 | P0、P1 | 乱序或晚到响应不写错文档；预算与限流可测试 |
| P3 局部文本闭环 | 选中页改写、差异预览、主线程应用 | P2 | 手动编辑与撤销触发冲突；关键事实与结构保留 |
| P4 少量模板闭环 | 2～3 套语义槽位、实例化、资源映射、排版验证 | P0、P1 | 中文替换、页复制与 PPTX 回读通过；无示例残留 |
| P5 大纲到整篇 | 大纲卡片、模板选择、按页生成、草稿预览 | P2、P4 | 多页成功后一次应用；单页失败只重跑该页 |
| P6 共享接口与发布验收 | CLI/控制/MCP 入口、回归、基准与使用说明 | P3、P5 | 相同提交语义；核心 WASM 验证；真实样本质量与耗时记录 |

P4 可在契约与提交基础合并后独立推进，不必等待文本 UI 完成。
扩展视觉重排、图片生成、任务恢复与更多模板作为后续独立提案。

### 最低回归矩阵

- 第 N 个补丁失败或提交 panic：文档、选区、历史与幂等状态保持不变。
- 多页完整提交：只有一条历史，Undo/Redo 恢复准确。
- 任务期间手动改字、删页、调序、撤销或重做：拒绝过期提交。
- 只改变选区：不触发内容冲突；切换文档不改变任务绑定。
- 关闭文档、取消任务、重复应用、乱序响应：不误写、不重复加页。
- 用户撤销 AI 结果后旧响应重试：不自动重新应用。
- 指针交互未结束：不吞并用户历史，结束后重新检查内容身份。
- 超长中文、缺字体、混合格式、无效 ID、超大响应：有界失败或明确降级。
- 模板复制页：母版、媒体、链接与 ID 映射正确，导出 PPTX 后回读一致。
- fake provider 固定输出可复现；真实模型验收不得只看工具返回成功。

代码阶段运行相关 crate 测试、`cargo fmt --check` 与 `cargo clippy --all-targets`；
集成阶段运行工作区测试、`cargo xtask layers` 和 `cargo xtask wasm`。
UI 功能使用控制通道截图或 CLI 渲染检查，能力完成后同步 `ROADMAP.md`。

## 10. 协作与上游同步

- 自有仓库：<https://github.com/hyperlook/deckcraft>，本地远程名 `origin`。
- 上游仓库：<https://github.com/storytold/deckcraft>，本地远程名 `upstream`。
- `main` 保持可运行；通过 PR 合并阶段分支，不直接在 `main` 开发 AI 功能。
- 以总 Issue 跟踪 P0～P6；实施每阶段时再创建子 Issue，关联总 Issue 与验收证据。
- PR 默认目标为 `hyperlook/deckcraft:main`，不是上游；需要贡献上游时单独提出。
- 同步前保持工作区干净：获取上游、快进本地 `main`、测试后推送 fork。
- fork 出现独有提交后，上游同步使用明确的集成分支与 PR；不强推 `main`。
- 未确认的本地修改不混入阶段提交，模板资产与凭据不随文档提交上传。

**决策依据**：以引擎提交边界保证用户完整改动的安全与撤销；以少量样本和确定性验证
建立可复现闭环，再增加模型自由度与模板覆盖面。
