# AI 助手：原文依据、大纲与页面文案

状态：修订后的产品约定，待实现。总追踪 [#10](https://github.com/hyperlook/deckcraft/issues/10)，上下文重建 [#20](https://github.com/hyperlook/deckcraft/issues/20)，最小模型入口与单页改写 [#15](https://github.com/hyperlook/deckcraft/issues/15)。架构与交付顺序见 [ai-assistant-architecture.md](ai-assistant-architecture.md)。

原 #13 的离线提取实现已封存在 `checkpoint/ai-context-extraction`，代码检查点 `7ae7951`。提取、来源、诊断、草稿与原生保存可复用；“摘录确认成大纲”未通过产品验收。当前代码尚未符合下列新语义，不能将计划描述为已有能力。

## 用户在做什么

用户自己知道改哪几个字时，会自己改，那次修改和 AI 无关。

交给 AI 的，是整页看着不对、又说不清该怎么动。AI 需要知道全稿在讲什么、该页要承担什么作用，再给出新的讲法。用户不应先手工把整稿重新整理成大纲，才能让 AI 开始工作。

## 三个对象，不混用

| 对象 | 是什么 | 不是什么 |
|---|---|---|
| 原文依据与素材 | 原稿文字、数字、条件、笔记、图片说明及来源/覆盖 | 现实真实性保证，或允许模型自行读取文件的路径 |
| 大纲 | 商量好的全稿主线、每页作用和简要表达意图 | 当前文本框全部文字，或唯一的事实仓库 |
| 页面文案与提案 | 页面最终标题/正文，或待接受的新讲法 | 应直接全文回填大纲的内容 |

已有 PPT 可以反向归纳大纲；这只能推断原作者意图，须由用户确认。提取到文字不等于理解文稿，确认摘录也不等于完成语义提炼。

## 当前文稿：先读全稿，再生成候选大纲

```mermaid
flowchart LR
    D[导入 PPTX / 当前原生文稿] --> E[只读提取原文依据与覆盖]
    E --> S[预览发送范围并授权发送]
    S --> M[AI 结合全稿归纳]
    M --> C[全稿主线 + 每页简要意图]
    C --> U[用户修正确认]
    U --> O[确认大纲；不改页面]
    O --> P[原生项目保存恢复]
```

- 默认保留原页映射和顺序，只归纳各页作用；重新分配内容、增删页或重排属于另行选择的重构。
- 全稿上下文包括页顺序、可读原文和来源/缺口。不是默认上传整份 PPTX、图片二进制、路径或聊天历史。
- 超预算时显式阻止或采用有界分段后综合；不能只取前 64 页却声称通篇理解，也不能逐页独立生成后假称理解全稿关系。
- 图片、图表、表格、备注等未读部分明确展示。用户可以补充说明，不能编造要点，也不要求重写其他页面。
- 原文在证据区显示；大纲编辑区显示模型提炼出的简要意图，而不是原段落默认副本。
- 授权发送原文与确认候选大纲是两个动作。归纳请求不要求先有已确认大纲，不复用 `Round::from_confirmed` 作为前置。
- 已有符合新契约的确认大纲默认复用。旧检查点 Outline 可能包含全文摘录，必须明确兼容/迁移，不仅检查字段存在。
- 提取、请求、编辑候选、取消和失败不改变页面或确认大纲。确认通过 engine 命令保存，可一步撤销/重做；暂存与确认状态分开。

## 一轮改页的依据

| 输入 | 含义 |
|---|---|
| 总大纲 | 全稿主线与目标页意图，指导表达方向 |
| 原文依据与素材 | 支撑数字、条件和断言，保留相关来源 |
| 点名的那一页 | 可信宿主绑定的 `docUid + pageId`，不是屏幕页码 |
| 这一轮意见 | 用户希望怎样改变讲法，不自动当作新的事实来源 |

简要大纲不能独自承载全部事实；改页请求必须能采用相关原文依据。模型不把素材内容当工具或系统指令。用户可显式补充事实为素材，不能仅靠“已确认”标签保证其真实性。

手改页面不会静默反写大纲。原文依据可显式刷新并显示差异/版本，再由用户决定是否重新归纳；不可每轮从画布抓字覆盖确认计划。

## 接受页面提案

提案是该页的新讲法，正文要点可以变多变少。用户看完真实预览再接受。只替换明确的标题/正文，保留图片、表格、组合、页脚与版式。失败、目标页删除、文稿关闭、拖动未松开时不写入。

页面正文不再直接全文覆盖大纲。如果讲述意图不变，保留原大纲；如果意图变化，提案应包含独立简要大纲变更供用户一同审阅，接受时原子更新，一步撤销。该新契约待 #20 设计、#15 单页整合实施；检查点 `ai.accept` 尚有旧的全文回填行为。

拒绝、取消、网络失败不写稿、不清空确认上下文。等待时手改不自动使单页提案失效；不做冲突合并。撤销后允许再次接受同一提案，相同内容重放不增加历史。

## 保存与复用

- `.deckcraft` 是项目文件，保存原文依据、大纲、素材、来源/覆盖、必要草稿与兼容版本；导入和未来 AI 新建使用同一项目保存机制。
- PPTX 是导出格式，不保证 AI 元数据。普通保存 PPTX 不能把未落盘元数据伪装为已安全保存；提示原生另存或保留未保存状态，具体机制由 #20 实施。
- 重开原生项目复用确认大纲，草稿仍未确认。只存在侧栏内存中的编辑不冒称已保存。
- 单独重导入外部 PPTX 默认新项目，不承诺缓存找回大纲。外部文件关联缓存另定义稳定身份、源变化检测、清理与隐私；运行期 `docUid` 不是跨次打开身份。
- AutoRecover 用于异常恢复，不代替正常项目库，也不覆盖未进入文稿的侧栏工作副本。

## 最小真实模型入口先做

复用 #15 的可选本地 Pi SDK 桥接与既有认证。最小界面包括模型选择、发送范围、请求/取消、结果与错误展示，不先建设完整聊天助手、OAuth 或通用 Provider 框架。

先非敏感真实 smoke，再 #20 全稿归纳与人工验收，最后 #15 单页改写。没有旧 #13 大纲确认验收前置，不要求 #15 整体关闭才能进入 #20。

认证不复制 token，不继承 coding 会话，不启动带工具的 agent。宿主负责 I/O 和请求生命周期，ai 负责内容契约，engine 是唯一文稿写入边界，UI 不发模型请求、不直接改 Presentation。凭据不进入文稿、IPC、日志或截图。

## 明确不做

- 不要求新旧段落数一致，不恢复旧“原位换词”方案。
- 不做多页并发 agent、冲突合并、任意工具执行或视觉重设计。
- 不把样张追加到文稿末尾当作修改目标页。
- 不预建全局文稿库、OCR、PDF/Office 素材解析或自动 URL 抓取。
- 不用 Fake 或测试通过代替真实归纳质量与人类产品验收。
